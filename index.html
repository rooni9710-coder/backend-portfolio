PROJECT 01

쿠팝비즈 | 다우오피스 연동형 모바일 쿠폰 선물 서비스

2025.01 – 현재 · 운영 및 개발

프로모션 정책, 쿠폰 발행, 판매 수량 보정 등 금전이 직접 걸린 로직을 담당하고 있습니다. 일 평균 약 500건의 쿠폰이 발행되며, 발행된 쿠폰은 곧 비용이기 때문에 수량이 한 건이라도 어긋나면 손실로 이어지는 환경에서 개발해 왔습니다.

담당 범위 · 프로모션 수량 제한 기능 개발, 판매 수량 보정 배치, 1인당 제한의 사용자 단위 분산락 적용.

프로모션 구매 수량 제어

사업팀 요청으로 대규모 프로모션에 수량 제한 기능을 신규 개발했습니다. 대표 사례는 아메리카노 100원 프로모션(1인당 1개 · 총 1,000개 한정)으로, 저가 프로모션 특성상 오픈 직후 요청이 집중되는 조건이었습니다.

문제와 제약

1인당 1개와 총 1,000개는 각각 사용자 이력과 공통 판매 수량을 확인해야 하는 제약입니다. 초과 판매가 비용으로 이어질 수 있어 총수량 상한을 지키는 것을 우선했습니다. 서로 다른 사용자가 같은 행을 동시에 갱신하므로 조회 후 저장만으로는 상한을 지킬 수 없습니다. MyBatis 기반 코드에서는 JPA 버전 컬럼 대신 판매 수량 자체를 비교 조건으로 사용했습니다.

판단과 구현
  • 1인당 1개 — 동일 사용자의 발행 이력을 조회해 기존 발행 건이 있는 경우 차단. 이 조회와 총수량 조건부 UPDATE는 같은 트랜잭션에서 처리
  • 총 1,000개 — 판매 수량 값 자체를 버전으로 활용하는 낙관적 락으로 설계
    • 조회한 판매 수량으로 상한을 먼저 확인하고, UPDATE 조건절에도 sold < 1000과 sold = 조회값을 함께 적용. 전자는 총수량 상한을 지키고, 후자는 조회 이후 다른 요청이 판매 수량을 바꾼 경우 갱신되지 않도록 처리
    • 영향 행 수가 0이면 다른 요청이 먼저 수량을 변경했거나 상한에 도달했을 가능성이 있으므로, 재시도 없이 해당 구매 요청을 실패 처리
총수량은 상한과 조회값을 모두 조건으로 둔 UPDATE로 제어했고, 해당 프로모션의 한정 수량 1,000개가 최종 모두 판매됐습니다. 1인당 제한은 기존 발행 이력을 조회해 선행 발행 여부를 확인했습니다.
동시 요청 대응
당시에는 발행 이력 조회로만 1인당 제한을 확인해, 동일 사용자의 동시 요청 두 건이 모두 통과할 수 있었습니다(해당 프로모션에서 같은 사용자에게 두 개가 발급된 확인 사례는 없음).

이후 (프로모션, 사용자) 단위 Redis 분산락을 적용해 발행 이력 확인부터 발행까지를 보호하도록 개선했습니다. 락을 얻지 못한 요청은 대기 없이 즉시 실패시키고, 전용 에러 응답으로 이미 처리 중인 요청임을 안내합니다.
PROJECT 01

쿠팝비즈

수량 정합성 · 동시성 제어

쿠폰 생명주기와 수량 정합성

쿠폰은 발행 이후 사용 또는 폐기 상태로 전이되며, 폐기 시 판매 수량이 복원되어야 합니다. 부분 사용은 프로모션 상품 대상에서 제외하는 정책이라 상태 자체는 단순합니다.

문제와 제약

외부 발행 요청 실패, 알림톡 발송 요청 실패, 어드민 폐기처럼 판매 수량을 되돌려야 하는 경로가 여러 곳이었습니다. 복원은 원자적 감소 UPDATE로 처리했습니다. 어느 경로에서든 복원이 누락되면 판매 수량이 실제보다 높게 남아, 판매 가능한 수량이 적게 보일 수 있습니다.

판단과 구현
  • 실시간 복원 경로를 유지하면서, 프로모션 진행 중에도 1시간 주기 배치로 판매 주문 이력 건수를 다시 집계해 판매 수량을 보정
  • 보정 UPDATE에 기존 판매 수량의 일치 조건을 두어 동시 변경을 감지. 갱신이 실패하면 판매 주문 이력을 다시 집계하고 최대 3회 재시도
원자적 감소로 즉시 복원하고, 진행 중에도 판매 주문 이력과 수량을 대조·보정하는 배치를 마련했습니다. 배치 갱신 충돌 시 재집계 후 최대 3회 재시도하도록 구성했습니다.

다우오피스 차세대 — 메신저 서버 신규 구축

2024.04 – 2024.12 · Backend 2명 / Frontend 1명 중 Backend 담당 · 오픈 전 개발 단계까지 참여

기존 그룹웨어 메신저는 Openfire 오픈소스에 의존하고 있어 기능 확장과 장애 대응에 제약이 있었습니다. 백엔드 2명·프론트엔드 1명이 참여한 차세대 프로젝트에서 WebSocket 기반 Spring STOMP 서버를 새로 구축했습니다.

담당 범위 · 주요 조회 API와 STOMP 통신 모듈의 구독 처리, SEND 수신·검증, MESSAGE 전달, 읽음 판단·조회 로직 재구현. 메시지 전달 구조는 팀 설계이며, 읽음 DB 구조는 DBA와 함께 검토했습니다.

주요 구현

  • 대화방 목록, 채팅 목록 조회 등 주요 조회 API 개발
  • STOMP 기반 실시간 통신 스펙을 프론트엔드와 협의하여 설계 및 개발
    • SEND 수신 시 메시지·UUID 형식 검증과 금칙어 필터링 후 RabbitMQ로 전달
    • 저장이 끝난 메시지를 Redis Pub/Sub으로 받아 구독자에게 MESSAGE로 전달
    • 대화방 입장: STOMP 구독 처리와 입장 시점(lastReadAt) 전달
  • 읽음 처리 DB 구조 변경에 따른 조회 로직 재구현
  • 채팅방 목록 조회 등 복잡한 쿼리를 네이티브 쿼리에서 QueryDSL로 전환
PROJECT 02

메시지 전달 구조 — 저장과 실시간 전송 분리

팀 설계 구조 · 본인 담당: STOMP 통신 모듈
문제와 제약
  • 업무 메신저이므로 실시간 전달과 함께 대화 기록 보존이 핵심 요구사항
  • 서버가 여러 Kubernetes 파드로 운영돼 송신자와 수신자가 서로 다른 파드에 연결될 수 있음
구조와 구현
  • 팀 설계로 DB 저장과 실시간 전송을 별도 모듈로 분리해, 저장이 끝난 메시지만 실시간 전달
  • 본인이 담당한 STOMP 통신 모듈에서 SEND 메시지와 UUID 형식을 검증하고 금칙어를 필터링한 뒤 RabbitMQ로 전달
  • 처리 모듈이 DB 저장 후 Redis Pub/Sub으로 발행하면, 각 파드의 STOMP 통신 모듈이 구독자에게 MESSAGE로 전달
  • Redis INCR로 발급한 시퀀스 ID를 정렬 기준으로 사용하고, 재연결 시 마지막 수신 ID 이후를 조회하는 API로 누락 구간을 보완
  • 대화방 입장 시점(lastReadAt)을 구독자에게 실시간 전달해 읽음 수에 반영
트레이드오프와 한계
Redis Pub/Sub은 연결이 끊긴 순간의 메시지를 보관하지 않아 실시간 전달 누락을 재연결 조회로 보완했습니다. 프론트가 생성한 UUID는 형식만 검증해 같은 UUID의 재전송은 차단하지 않았습니다.
개선 방향(미적용) · UUID 기준 Redis SETNX(TTL)나 DB 유니크 제약으로 중복 전송을 차단할 수 있습니다.
팀이 설계한 저장·전송 분리 구조에서 STOMP 통신 모듈의 구독 처리, SEND 검증·필터링, 여러 파드 구독자에게 MESSAGE 전달을 구현했습니다.
PROJECT 02

읽음 처리 구조 재설계

읽음 상태 저장량의 증가 기준을 바꾼 사례
문제와 제약
  • 메시지 1건당 대화방 멤버 수(N)만큼 읽음 레코드를 별도 테이블에 저장
  • 구조적 예시: 메시지 1,000건이면 10명 대화방에서 1만 행, 50명 대화방에서 5만 행이 필요
  • 읽음 데이터가 메시지 수 × 멤버 수로 증가해, 오래 유지되는 대화방일수록 데이터량과 조회 비용이 함께 증가
판단과 구현
  • DBA와 구조 검토를 거쳐, 대화방 멤버 단위로 마지막 읽음 시점(lastReadAt) 1행만 관리하는 방향으로 DB 구조 변경
  • 변경된 구조에 맞춰 읽음/미읽음 판단 로직을 애플리케이션 단에서 재구현
    • 메시지 조회 시 lastReadAt 기준 시각 비교로 판단
    • 읽음 테이블 제거에 따라 대화방 목록·메시지 조회 쿼리에서 해당 조인 삭제
  • 위 구조적 예시의 동일 조건에서 읽음 상태 저장 행 수가 10행·50행으로 변경
트레이드오프
특정 메시지의 미읽음 멤버 목록을 단일 조회로 가져올 수 없게 되지만, 당시 해당 요구사항이 없었고 필요 시 멤버별 lastReadAt과 메시지 시각을 비교해 계산 가능하다고 판단했습니다. 대화방 규모가 최대 50명 수준이라 비교 연산 비용이 크지 않다는 점도 근거였습니다.
읽음 상태 저장 행 수를 메시지 수 × 멤버 수에 비례하던 구조에서 멤버 수에 비례하는 구조로 바꿨습니다. 1만 행 → 10행은 운영 실측이 아닌 10명·메시지 1,000건의 구조적 예시입니다.
PROJECT 03

다우오피스 차세대 — 통합 알림 서버 신규 구축

2023.10 – 2024.02

여러 그룹웨어 서비스가 공통으로 사용할 알림 서버를 신규 설계·구축했습니다.

담당 범위 · FCM 발송 기능과 채널 확장 인터페이스, Spring AMQP BatchListener를 이용한 발송 흐름, 토큰별 오류 처리, 재시도·DLQ 처리.

메시지 큐 도입 — 알림 요청과 발송 분리

문제와 제약

기존 그룹웨어 알림은 큐 없이 처리되어, 대량 알림이 발생하면 DB 부하가 크게 증가한다는 의견을 DBA로부터 공유받았습니다.

판단과 구현
  • 알림 요청과 실제 발송을 RabbitMQ로 분리해, 요청 서비스는 큐에 메시지를 넣고 반환하고 몰린 요청은 컨슈머 처리 속도에 맞춰 발송
  • 사내에서 이미 운영 중인 RabbitMQ를 사용. Kafka는 신규 운영 부담을 고려해 도입하지 않음
  • 일시적 오류는 컨슈머 안에서 지수 백오프로 최대 3회 재시도하고, 이후에도 실패한 건은 DLQ로 전달
  • 500건 배치 중 일부만 실패하면 배치 전체를 ack하고 실패 건만 DLQ로 보내 성공 건의 재발송을 방지
트레이드오프
요청 서비스의 응답과 발송 부하는 분리되지만, 알림 도착은 큐 대기만큼 늦어질 수 있습니다. 또한 컨슈머 안에서 기다렸다가 재시도하므로, 대기 중에는 해당 컨슈머가 다음 배치를 처리하지 못합니다.

확장을 전제한 구조 설계

  • FCM 기반 크로스 플랫폼 Push 알림 서비스 설계 및 개발
  • 포트 앤 어댑터 패턴 기반 멀티 모듈 구조로 알림 채널 확장 지점을 인터페이스로 분리
    • 새로운 알림 채널이 추가되어도 기존 발송 로직을 수정하지 않도록 구성

외부 API 제약에 맞춘 대량 발송 설계

문제와 제약

FCM Admin SDK의 묶음 발송 메서드는 한 번에 입력받는 메시지 또는 토큰이 최대 500건으로 제한됩니다. 같은 내용을 여러 사람에게 보내는 공지성 알림에는 sendEachForMulticast, 알림 내용이 수신자마다 다른 경우에는 sendEach를 사용했습니다. 큐 소비 단위가 입력 한도를 넘지 않도록 500건으로 맞췄습니다.

판단과 구현
  • 대용량 알림 발송 시 Spring AMQP BatchListener로 큐 소비 단위를 500건으로 맞춰, SDK 입력 한도를 넘지 않도록 구성
    • 소비한 배치를 별도로 분할하는 로직을 줄임
  • 발송 결과를 토큰 단위로 분기 처리
    • UNREGISTERED 등 무효 토큰으로 확인된 건만 삭제해 누적을 방지
    • 일시적 오류는 지수 백오프로 최대 3회 재시도하고, 이후 실패 건은 DLQ로 전달
큐 소비 단위와 FCM SDK의 입력 한도를 맞춰 별도 분할 로직을 줄이고, 토큰별 영구 실패와 일시적 오류의 후속 처리를 분리했습니다.

초기 접속 부하 대응 — 정적 자산 사전 압축

문제와 제약

프론트엔드 정적 리소스의 초기 로드 용량은 회원가입 페이지 약 9MB, 별도로 측정한 다른 페이지 약 12~16MB였습니다. 초대 메일 발송 직후 접속이 집중될 수 있어 초기 로드 부담을 줄일 필요가 있었습니다.

판단과 대안
  • Apache mod_deflate로 요청 시점에 실시간 압축 — 구현은 간단하나, 접속이 몰리는 순간 압축 연산이 CPU를 점유해 병목이 될 수 있다고 판단
  • 빌드 시점에 .gz로 사전 산출 — 요청 시점의 압축 연산을 제거할 수 있다고 판단

트래픽이 집중되는 시점에 서버 연산을 늘리지 않는 쪽이 맞다고 보고 사전 압축 방식을 선택했습니다.

초대 메일 발송 처리 개선

문제와 제약

초대 대상이 수천 명 규모라, 단일 흐름에서 순차 발송 시 요청이 장시간 점유됩니다. 발송을 비동기로 전환하면 발송 결과를 요청 응답으로 즉시 돌려줄 수 없다는 문제가 새로 생깁니다.

판단과 구현
  • 500건 단위 chunk로 분할하고 @Async + ThreadPoolTaskExecutor 기반 비동기 발송으로 전환
    • chunk 크기 500은 사업팀이 지정한 발송 단위를 따랐고, 가짜 주소 10,000건이 연속 실패하는 조건에서도 후속 chunk 처리와 실패 결과 수집이 중단되지 않는지 확인
    • 스레드 풀은 5로 구성. 메일 발송은 외부 서버 응답 대기가 대부분인 I/O 구간이라 스레드를 늘려도 처리량이 비례하지 않고, 수신 측에 과도한 부하로 보일 수 있어 보수적으로 설정
  • 결과 전달 경로를 별도로 설계 — 발송 실패 건을 수집해 엑셀 파일로 생성, 초대를 실행한 마스터 사용자에게 결과 파일을 첨부한 메일로 전송
    • 실패한 대상자를 담당자가 직접 확인하고 재조치할 수 있도록 구성
메일 발송을 요청 처리와 분리하고, 실패 대상을 확인해 후속 조치할 수 있는 경로를 마련했습니다.
