PROJECT 01

쿠팝비즈 | 다우오피스 연동형 B2E 모바일 쿠폰 선물 서비스

2025.01 – 현재 · 운영 및 개발

프로모션 정책, 쿠폰 발행, 판매 수량 보정 등 금전이 직접 걸린 로직을 담당하고 있습니다. 일 평균 약 500건의 쿠폰이 발행되며, 발행된 쿠폰은 곧 비용이기 때문에 수량이 한 건이라도 어긋나면 손실로 이어지는 환경에서 개발해 왔습니다.

담당 범위 · 프로모션 수량 제한 기능 개발, 판매 수량 보정 배치, 1인당 제한의 사용자 단위 분산락 적용.

총수량 상한과 동일 사용자 주문 경쟁을 분리해 제어

사업팀 요청으로 대규모 프로모션에 수량 제한 기능을 신규 개발했습니다. 대표 사례는 아메리카노 100원 프로모션(1인당 1개 · 총 1,000개 한정)으로, 저가 프로모션 특성상 오픈 직후 요청이 집중되는 조건이었습니다.

문제와 제약

1인당 1개와 총 1,000개는 각각 사용자 이력과 공통 판매 수량을 확인해야 하는 제약입니다. 초과 판매가 비용으로 이어질 수 있어 총수량 상한을 지키는 것을 우선했습니다. 서로 다른 사용자가 같은 행을 동시에 갱신하므로 조회 후 저장만으로는 상한을 지킬 수 없습니다. 초기에는 MyBatis 조건부 UPDATE로 갱신 시점의 충돌을 감지했지만, 수량이 남아 있어도 충돌한 요청은 실패하는 한계가 있었습니다.

판단과 구현
  • 1인당 1개 — 동일 사용자의 주문 이력을 조회해 기존 주문 건이 있는 경우 차단. 이 조회와 총수량 조건부 UPDATE는 같은 트랜잭션에서 처리
  • 총 1,000개 · 초기 설계 — sold < 1000 AND sold = 조회값으로 상한과 조회값을 비교하는 낙관적 락 적용
    • 비관적 락이나 외부 락 없이 갱신 시점의 조건 검사로 충돌을 감지. 영향 행이 0이면 재시도 없이 실패 처리했으나, 재고가 남아도 충돌로 구매가 실패할 수 있었음
  • 후속 개선 · 운영 배포 — 조회값 비교를 제거하고 sold = sold + 1 WHERE sold < 1000으로 변경
    • 한 번의 UPDATE로 상한 검사와 증가를 함께 처리해, 수량이 남아 있을 때의 충돌 실패를 제거
    • 영향 행 1이면 주문 생성을 진행하고, 0이면 매진으로 즉시 안내. 매진 후 재시도는 결과를 바꾸지 않고 DB 부하만 늘리므로 재시도하지 않음
초기 총수량 제어를 적용한 프로모션은 한정 1,000개를 판매 상한 초과 없이 전량 판매했습니다. 이후 원자적 조건부 증가로 충돌 실패를 제거하고, 1인당 제한에는 사용자별 분산락을 운영 적용했습니다.
한정 수량 프로모션 약 40회 · 판매 상한 초과 0건
동시 요청 대응
당시에는 주문 이력 조회로만 1인당 제한을 확인해, 동일 사용자의 동시 요청 두 건이 모두 통과할 수 있었습니다(해당 프로모션에서 같은 사용자에게 두 개가 발급된 확인 사례는 없음).

이후 (상품 ID, 사용자 ID) 단위 Redisson 분산락을 적용해 주문 이력 확인부터 주문 생성 트랜잭션 커밋까지를 보호하도록 개선했습니다. 쿠폰 발행은 커밋 이후 메시지 큐를 통해 비동기로 진행됩니다. 락을 얻지 못한 요청은 대기 없이 즉시 실패시키고, 전용 에러 응답으로 이미 처리 중인 요청임을 안내합니다.
운영 정합성 보완: 판매 수량 복원과 정기 보정
  • 외부 쿠폰 발행 실패·어드민 폐기 시 원자적 감소 UPDATE로 판매 수량을 복원했습니다. 알림톡 실패는 주문·판매 수량을 유지하고 수동 재발송과 Slack 알림으로 대응했습니다.
  • 1시간 주기로 주문 이력을 집계해 판매 수량을 보정했습니다. 보정 UPDATE에 기존 수량 일치 조건을 두고, 충돌하면 재집계 후 최대 3회 재시도했습니다.

주요 구현

  • 읽음 처리 DB 구조 변경에 따른 조회 로직 재구현

PROJECT 02

메시지 전달 구조 — 저장과 실시간 전송 분리

팀 설계 구조 · 본인 담당: 송신 REST API · STOMP 통신
문제와 제약
  • 업무 메신저이므로 실시간 전달과 함께 대화 기록 보존이 핵심 요구사항
  • 서버가 여러 Kubernetes 파드로 운영돼 송신자와 수신자가 서로 다른 파드에 연결될 수 있음
구조와 구현
  • 팀 설계로 DB 저장과 실시간 전송을 별도 모듈로 분리해, 저장이 끝난 메시지만 실시간 전달
  • 본인이 담당한 메시지 송신 REST API에서 메시지와 UUID 형식을 검증하고 금칙어를 필터링한 뒤 RabbitMQ로 전달
  • 처리 모듈이 DB 저장 후 Redis Pub/Sub으로 발행하면, 각 파드의 STOMP 통신 모듈이 구독자에게 MESSAGE로 전달
  • Redis INCR로 발급한 시퀀스 ID를 정렬 기준으로 사용하고, 재연결 시 마지막 수신 ID 이후를 조회하는 API로 누락 구간을 보완
  • 대화방 멤버의 마지막 읽음 시퀀스(lastReadMessageSeqId)를 구독자에게 전달해 읽음 수에 반영
트레이드오프와 한계
Redis Pub/Sub은 연결이 끊긴 순간의 메시지를 보관하지 않아 실시간 전달 누락을 재연결 조회로 보완했습니다. 프론트가 생성한 UUID는 형식만 검증해 같은 UUID의 재전송은 차단하지 않았습니다.
개선 방향(미적용) · UUID 기준 Redis SETNX(TTL)나 DB 유니크 제약으로 중복 전송을 차단할 수 있습니다.
팀이 설계한 저장·전송 분리 구조에서 메시지 송신 REST API의 검증·필터링과 STOMP 구독 처리, 여러 파드 구독자에게 MESSAGE 전달을 구현했습니다.
PROJECT 02

메시지별 읽음 상태를 멤버별 시퀀스로 변경

읽음 상태 저장량의 증가 기준을 바꾼 사례
문제와 제약
  • 메시지 1건당 대화방 멤버 수(N)만큼 읽음 레코드를 별도 테이블에 저장
  • 구조적 예시: 메시지 1,000건이면 10명 대화방에서 1만 행, 50명 대화방에서 5만 행이 필요
  • 읽음 데이터가 메시지 수 × 멤버 수로 증가해, 오래 유지되는 대화방일수록 데이터량과 조회 비용이 함께 증가
판단과 구현
  • DBA가 제안한 구조를 검토하고, 대화방 멤버 단위로 마지막 읽음 시퀀스(lastReadMessageSeqId) 1행을 관리하는 구조에 맞춰 조회·판단 로직 구현
  • 변경된 구조에 맞춰 읽음/미읽음 판단 로직을 애플리케이션 단에서 재구현
    • 메시지의 seqId와 lastReadMessageSeqId를 비교해 판단
    • 읽음 테이블 제거에 따라 대화방 목록·메시지 조회 쿼리에서 해당 조인 삭제
  • 위 구조적 예시의 동일 조건에서 읽음 상태 저장 행 수가 10행·50행으로 변경
트레이드오프
특정 메시지의 미읽음 멤버 목록을 단일 조회로 가져올 수 없게 되지만, 당시 해당 요구사항이 없었고 필요 시 멤버별 lastReadMessageSeqId와 메시지 seqId를 비교해 계산 가능하다고 판단했습니다. 대화방 규모가 최대 50명 수준이라 비교 연산 비용이 크지 않다는 점도 근거였습니다.
읽음 상태 저장 행 수를 메시지 수 × 멤버 수에 비례하던 구조에서 멤버 수에 비례하는 구조로 바꿨습니다. 1만 행 → 10행은 운영 실측이 아닌 10명·메시지 1,000건의 구조적 예시입니다.
PROJECT 03

삼일회계법인 전용 복지몰 구축

2026.05 – 2026.08 (오픈) · 풀스택 2명

기존 복지몰 플랫폼 위에 약 4,000명의 임직원을 대상으로 하는 고객사 전용 사이트를 구축했습니다. 초대 메일을 받은 임직원이 링크로 가입하는 구조여서 발송 직후 접속 집중에 대비해야 했습니다.

담당 범위 · 정적 자산 사전 압축과 Apache 서빙 설정, 초대 메일 처리, k6 부하 테스트. 프로젝트는 풀스택 2명이 함께 진행했습니다.

gzip 사전 압축으로 빌드 산출물 68.5% 절감

문제와 제약

프론트엔드 정적 리소스의 초기 로드 용량은 회원가입 페이지 약 9MB, 별도로 측정한 다른 페이지 약 12~16MB였습니다. 초대 메일 발송 직후 접속이 집중될 수 있어 초기 로드 부담을 줄일 필요가 있었습니다.

판단과 대안
  • Apache mod_deflate로 요청 시점에 실시간 압축 — 구현은 간단하나, 접속이 몰리는 순간 압축 연산이 CPU를 점유해 병목이 될 수 있다고 판단
  • 빌드 시점에 .gz로 사전 산출 — 요청 시점의 압축 연산을 제거할 수 있다고 판단

트래픽이 집중되는 시점에 서버 연산을 늘리지 않는 쪽이 맞다고 보고 사전 압축 방식을 선택했습니다.

정적 자산 사전 압축 · 초대 메일 발송

초대 발송을 비동기로 분리하고 실패 결과를 메일로 제공

문제와 제약

초대 대상이 수천 명 규모라, 단일 흐름에서 순차 발송 시 요청이 장시간 점유됩니다. 발송을 비동기로 전환하면 발송 결과를 요청 응답으로 즉시 돌려줄 수 없다는 문제가 새로 생깁니다.

판단과 구현
  • 초대 요청 1건을 @Async 작업 1개로 제출하고, 선택된 스레드가 대상자를 500명 단위로 나눠 순차 발송
    • chunk 크기 500은 사업팀이 지정한 발송 단위를 따랐고, 더미 이메일 주소 10,000건이 연속 실패하는 조건에서도 후속 청크 처리와 실패 결과 수집이 중단되지 않는지 확인
    • 메일 발송용 스레드 풀은 core/max 5로 구성하고, 동시에 최대 5개의 초대 요청을 처리하도록 설정
  • 결과 전달 방식을 기획팀에 제안하고 구현 — 발송 실패 건을 수집해 엑셀 파일로 생성, 초대를 실행한 마스터 사용자에게 결과 파일을 첨부한 메일로 전송
    • 실패한 대상자를 담당자가 직접 확인하고 재조치할 수 있도록 구성
메일 발송을 요청 처리와 분리하고, 실패 대상을 확인해 후속 조치할 수 있는 경로를 마련했습니다.

k6 부하 테스트 — 오픈 전 검증과 사후 재측정

2026.08 오픈 · 2026-10-07 스테이징 사후 측정 (Apache + Vue SPA)

오픈 전 테스트는 랜딩·약관 URL 응답만 측정해 실제 화면 로딩을 반영하지 못했습니다.

사후 재측정 — 신규 방문 기준 gzip ON/OFF

복지몰 오픈 이후 스테이징에서 신규 방문 1회를 메인 HTML 1개 + 정적 리소스 19개 병렬 다운로드로 구성했습니다. 캐시 없이 초당 유입을 고정하는 open model로 단계마다 120초 유지했습니다.

ON은 Accept-Encoding: gzip, deflate, br, OFF는 Accept-Encoding: identity로 압축하지 않은 원본을 요청했습니다.

이전 ON 측정은 6명/초 p95 3.05초였습니다. 일부 경로가 HTML 대체 응답이라 조건이 달랐고, 편차 원인은 확인하지 못했습니다.
이번 측정에서는 유사한 p95 수준에서 OFF 2명/초(2.76초) → ON 8명/초(2.74초)로 초당 유입이 4배인 조건을 확인했습니다. OFF는 압축하지 않은 원본 전송 조건이며 실시간 압축과의 비교는 아닙니다. 스테이징·단일 부하 PC·캐시 없는 신규 방문 기준입니다.

시나리오 2 — 초대 메일 발송

  • 더미 이메일 주소 10,000건을 대상으로 chunk 분할, 비동기 처리와 실패 결과 수집이 연속 실패 상황에서도 중단되지 않는지 검증
  • 대상 건수는 예상 이용 규모인 약 4,000명보다 크게 설정했으나, 실제 메일 수신 성공이나 정상 발송 처리량을 검증한 결과는 아닙니다.
  • 테스트 환경에서는 실제 수신 주소를 사용할 수 없어 더미 이메일 주소로 발송한 탓에 SMTP 단계에서 전량 수신 거부가 발생
    • 거부 결과를 포함한 10,000건의 대상 처리가 끝까지 진행됐습니다.
    • 발송 실패가 연속되는 조건에서도 스레드 풀이 고갈되거나 후속 청크 처리가 멈추지 않는 것을 함께 확인
신규 방문 측정에서 OFF 2명/초(p95 2.76초) → ON 8명/초(p95 2.74초), 실패 0건을 확인했습니다. 초대 메일은 연속 실패 조건에서도 흐름이 끊기지 않음을 별도로 검증했습니다. 요청 하나보다 사용자가 실제로 겪는 단위를 기준으로 판단합니다.

다우오피스 차세대 — 통합 알림 서버 신규 구축

2023.10 – 2024.02 · BE 2명

여러 그룹웨어 서비스가 공통으로 사용할 통합 알림 서버 신규 구축에 참여해, FCM 발송과 토큰별 오류·재시도 처리를 구현했습니다.

담당 범위 · 팀의 포트 앤 어댑터 기반 멀티 모듈 구조에서 FCM 발송 어댑터·채널 확장 인터페이스 구현. Spring AMQP BatchListener 발송 흐름, 토큰별 오류·재시도·DLQ 처리.

메시지 큐 도입 — 알림 요청과 발송 분리

문제와 제약

기존 그룹웨어 알림은 큐 없이 처리되어, 대량 알림이 발생하면 DB 부하가 크게 증가한다는 의견을 DBA로부터 공유받았습니다.

판단과 구현
  • 알림 요청과 실제 발송을 RabbitMQ로 분리해, 요청 서비스는 큐에 메시지를 넣고 반환하고 몰린 요청은 컨슈머 처리 속도에 맞춰 발송
  • 사내에서 이미 운영 중인 RabbitMQ를 사용. Kafka는 신규 운영 부담을 고려해 도입하지 않음
  • 일시적 오류는 컨슈머 안에서 지수 백오프로 최대 3회 재시도하고, 이후에도 실패한 건은 DLQ로 전달
  • 500건 배치 중 일부만 실패하면 FCM 응답을 받은 대상 중 실패 건만 후속 처리하고 배치를 ACK
트레이드오프
요청 서비스의 응답과 발송 부하는 분리되지만, 알림 도착은 큐 대기만큼 늦어질 수 있습니다. 또한 컨슈머 안에서 기다렸다가 재시도하므로, 대기 중에는 해당 컨슈머가 다음 배치를 처리하지 못합니다.

FCM 500건 한도에 맞춰 소비하고 실패 대상만 후속 처리

문제와 제약

FCM Admin SDK의 묶음 발송 메서드는 한 번에 입력받는 메시지 또는 토큰이 최대 500건으로 제한됩니다. 같은 내용을 여러 사람에게 보내는 공지성 알림에는 sendEachForMulticast, 알림 내용이 수신자마다 다른 경우에는 sendEach를 사용했습니다. 큐 소비 단위가 입력 한도를 넘지 않도록 500건으로 맞췄습니다.

판단과 구현
  • 대용량 알림 발송 시 Spring AMQP BatchListener로 큐 소비 단위를 500건으로 맞춰, SDK 입력 한도를 넘지 않도록 구성
    • 소비한 배치를 별도로 분할하는 로직을 줄임
  • 발송 결과를 토큰 단위로 분기 처리
    • UNREGISTERED 등 무효 토큰으로 확인된 건만 삭제해 누적을 방지
    • 일시적 오류는 지수 백오프로 최대 3회 재시도하고, 이후 실패 건은 DLQ로 전달
큐 소비 단위와 FCM SDK의 입력 한도를 맞춰 별도 분할 로직을 줄이고, 토큰별 영구 실패와 일시적 오류의 후속 처리를 분리했습니다. 다만 FCM 응답 후 ACK 전에 컨슈머가 중단되면 중복 발송 가능성이 남아 있어 정확히 한 번 처리로 설명하지 않습니다.
